01 / THE PROBLEM WHEN “LATE” MEANS “WRONG”

The right answer,
delivered too late.

A UAV controller must produce commands in time to respond to changes in flight state. A common architecture splits the work: a microcontroller stabilizes the aircraft while a Linux computer handles images, navigation or planning. When both kinds of work share one computer, the control task competes with applications and background services for the CPU. [1]

On a general-purpose kernel, a late command can leave an actuator steering by stale data. In a real-time system, correctness includes both the computed result and the time it becomes available. This project keeps the sensors and motors out of scope and asks a sharper question: what does the operating system itself cost, cycle after cycle? [1]

READ ONE TERM PRECISELY

Jitter is the variation of timing around the nominal schedule. Metrics in this dossier — percentiles and maxima — describe the tail: rare but large delays that a mean value hides. [1]

The control task runs at f = 250 Hz, so T = 1/f = 4,000 µs and the relative deadline D = T: every invocation must finish within 4 ms of its nominal release, following the model in [1].

  • RQ4Can kernel traces explain the largest observed delays?

STAGES M1 — M2 / STANDARD KERNEL

Trust the timer
before the payload.

M1 runs a latency pilot with cyclictest — one thread on CPU 2, priority 50, 4,000 µs interval, 2,500 iterations — testing the timer without the UAV payload. M2 integrates the control computation on the standard kernel and validates its outputs and CSV export. [14]

Clock discipline comes from CLOCK_MONOTONIC and absolute sleeps: releases stay on the t₀ + kT schedule, and an interrupted sleep retries the same target. [7]

COMPLETION CONDITION

Valid clock readings and logs for M1; correct payload outputs and a working CSV export for M2 — all before any RT configuration.

STAGES M3 — M4 / PREEMPT_RT

Bring in
the real-time kernel.

M3 boots a PREEMPT_RT kernel and confirms the evidence: CONFIG_PREEMPT_RT=y and a live /sys/kernel/realtime. M4 fixes CPU placement and pilots the environment — thermal behavior, memory pressure, and stress sized for this board. [2]

THE 4 GB CONSTRAINT

On a 4 GB board, memory stress must be piloted first — start near 1 GiB total (two workers × 512 MiB) — so the scheduling study never silently becomes a memory-exhaustion study.

STAGES M5 — M6 / MEASUREMENT & ANALYSIS

Run the matrix.
Read the tails.

32 configurations, at least three valid runs each: 500 warm-up cycles then 10,000 measured invocations per run, ~67.2 minutes of nominal workload. Kernel changes force reboots, so runs go in randomized blocks with the seed saved. [1]

M6 answers the research questions within the evidence: percentiles and maxima, time series for delay bursts, distributions per configuration — and kernel traces collected in separate diagnostic runs. [1]

How to read these numbers correctly

The bars show maxima of wake-up latency L under stress, measured on Raspberry Pi 5 with 8 GB RAM [1, table 4]. The deadline check in this project uses response time R = L + E — a small L alone never proves the 4 ms deadline is met, because the payload still has to execute.

Improvement is computed as Δ = 100 × (Mstandard − MRT) / Mstandard. Note the exceptions: SCHED_OTHER nice 0 got worse under RT on Pi 5 (8,626 → 9,015 µs), and FIFO priority 50 beat priority 99 under RT (160 vs 224 µs). Changing the kernel or raising priority does not guarantee improvement in every metric — each configuration earns its own verdict.

04 / INSIDE ONE CYCLE rₖ → sₖ → fₖ · EVERY 4 MS

Four beats,
ten thousand times.

Each of the 10,000 measured invocations follows the same rhythm. Timestamps are stored in nanoseconds and converted to microseconds only for presentation — no early rounding.

ONE INVOCATION OF τ SLEEP Until the planned release

Timing model per [1, §2.2]; sampling procedure of this project. [1]

STEP 01 / RELEASE rₖ

Sleep until
the planned release.

The program sleeps on CLOCK_MONOTONIC with TIMER_ABSTIME, so releases stay locked to the t₀ + kT grid — computation time never accumulates into the period. If a signal interrupts the sleep, it retries the same target; any other error stops the run. [7]

“The resolution reported by clock_getres does not establish wake-up accuracy.”Project sampling procedure · L must be measured directly [7]
STEP 02 / WAKE-UP

Open your eyes.
Pay the latency.

The first timestamp sₖ lands immediately after a successful return from the sleep. The gap L = sₖ − rₖ is the kernel's surcharge: scheduler decisions, timer machinery, interrupt paths. A negative L after a successful sleep is a bug alarm — check target generation, clock readings and signal handling.

WHAT L DOES NOT INCLUDE

L measures the wake-up only. The payload still has to run — which is why the deadline check uses R, never L alone.

STEP 03 / PAYLOAD

Attitude control,
then allocation.

The computational payload runs with predefined inputs held in memory: attitude-control computation followed by output allocation, following the reference workload [1]. The authors' implementation may be reused with its revision recorded [10]; any simplified implementation must be validated before timing is trusted.

E = fₖ − sₖ may include time spent preempted — it is not pure CPU demand, and it cannot directly size a DEADLINE budget.

STEP 04 / STORE & CHECK

Stamp it. File it.
Check the line.

The completion timestamp fₖ closes the sample: r, s and f go to preallocated RAM — CSV is written only after the run. The response R = fₖ − rₖ faces the 4 ms deadline; Rₖ > 4,000 µs counts as a miss.

THE OVERRUN RULE

After an overrun, the program skips elapsed release points and counts them — no catch-up bursts. The rule is fixed across all configurations, and both misses and skipped releases are reported.

06 / THE PLATFORM BCM2711 vs BCM2712 [6]

Older cores.
Shared cache.

The replication moves from Raspberry Pi 5 to Pi 4: Cortex-A72 instead of A76, one shared 1 MB L2 for the cluster instead of private L2 plus 2 MB L3, half the RAM. Differences may arise from CPU, cache hierarchy, kernel version or conditions — so the environment gets recorded, not assumed. [6]

Measured frequency on Pi 4 is to be confirmed on the board; the reference ran at 2.4 GHz [1]. Pinning reduces direct CPU competition, but cores still share memory — load elsewhere can stretch cache and DRAM access times.

WHILE THE KERNELS MUST MATCH

Same source, same tools,
one deliberate difference.

Standard and PREEMPT_RT kernels should come from the same source that supports Pi 4, with the same operating system, compiler, program revision and compiler options. If base versions differ, that is reported as a possible confounding factor. The paper disables RT bandwidth throttling (sched_rt_runtime_us = −1) for its runs; the learning stage here keeps the default and documents any change. [1]

07 / EXPECTED OUTCOMES PROPOSED — NOT PROMISED

Three hypotheses.
Zero results yet.

01

RT shrinks the tails

PREEMPT_RT reduces large delays with FIFO, RR or DEADLINE under mixed stress — evaluated on p99, maxima and repeated runs, not on means. [2]

02

Memory still bites

Memory load on other cores increases E or R even with the task pinned — shared cache and DRAM do not respect CPU boundaries. Separate load tests size the effect. [1]

03

Some configs pass

Several RT configurations are expected to meet both TC04 (every Rₖ ≤ 4 ms) and TC05 (max L ≤ 500 µs) on Pi 4. Failures demand configuration, payload and trace checks — not excuses. [1]

READ THE LIMITS BEFORE QUOTING ANY NUMBER

A run of 10,000 invocations at 250 Hz spans about 40 nominal seconds; its maximum describes those samples under those conditions. Repeated runs and retained raw data assess consistency — they do not replace WCET analysis, blocking-time analysis or flight-safety verification. Meeting CPU timing still leaves sensor and actuator timing to be evaluated separately. [1]

sudo apt install build-essential git stress-ng rt-tests

cat /sys/kernel/realtime   # expect: 1
zgrep CONFIG_PREEMPT_RT /proc/config.gz
# CONFIG_PREEMPT_RT=y is the evidence —
# chrt alone proves nothing

# after each run, on Windows:
scp -r your_user@pi_IP:~/uav-rt/logs .

# milestone 1: SSH + timer test done
# milestone 2: valid CSV, OTHER n0, idle
